- **Autor:** arquiteto-senior, 2026-11-17. Plano: `docs/plans/PLAN_M365_GRAPH_CONNECTORS.md`.

## Objetivo

Um leitor somente leitura, tipo `sharepoint_online`, que autentica um humano por device code (cliente público, sem segredo, escopos `Files.Read` + `offline_access`), lista e baixa só os arquivos de uma pasta configurada do OneDrive do usuário e passa cada arquivo pela mesma extração e detecção do conector de arquivos. A Fase 0 roda esse mesmo leitor contra o OneDrive pessoal do operador, numa pasta sintética, e registra o resultado como aconteceu.

## Risco

**Risco: alto.** Mexe em autenticação (OAuth público), em credenciais de vida longa (o refresh token vale 90 dias e não fica preso à pasta), em saída de rede para três classes de host (login, Graph e o host de download pré-autenticado) e numa fronteira de escopo que o token não impõe: `Files.Read` lê o drive inteiro, e quem restringe à pasta é o código. Um erro aqui vaza dados do cliente ou um token. Modelo do dev: o mais forte disponível; revisão de segurança do SHA obrigatória (cyber-senior).

## Contrato

### 1. Configuração do alvo

```yaml
targets:
  - name: onedrive-sintetico
    type: sharepoint_online
    auth:
      mode: delegated                  # único valor aceito nesta fase; app_only fica para #2262
      tenant: consumers                # consumers | organizations | common | GUID do tenant
      client_id_from_env: M365_CLIENT_ID   # nome da variável; ou client_id: <valor>, só em config efêmero
    drive: me                          # único valor aceito nesta fase
    root_folder: /DataBoar-Sintetico   # obrigatório (ou root_folder_id); nunca a raiz do drive
    max_depth: 32                      # opcional, 1..256
    max_file_bytes: 104857600          # opcional, 1 byte..2 GiB; padrão 100 MiB
    throttle_max_wait_seconds: 120     # opcional, 1..600
```

Regras de validação, todas no início de `run()`, antes de qualquer requisição (falha `config_error`, nenhuma chamada de rede):

- `auth.mode`: ausente vale `delegated`. `app_only` falha com "auth.mode app_only is not available yet (#2262)". Outro valor falha.
- `auth.tenant`: obrigatório; aceita exatamente `consumers`, `organizations`, `common` ou um GUID (`^[0-9a-fA-F]{8}-([0-9a-fA-F]{4}-){3}[0-9a-fA-F]{12}$`). Nada mais é interpolado na URL de login.
- `auth.client_id`: obrigatório depois da resolução do loader; formato GUID. A mensagem cita a chave, nunca o valor.
- `drive`: ausente vale `me`; outro valor falha ("drive selection is not available yet (#2262)").
- `root_folder` **xor** `root_folder_id`: exatamente um.
- `root_folder`: começa com `/`; dividido por `/`, cada segmento não vazio, diferente de `.` e `..`, sem `\`, sem caractere de controle e sem `* < > ? : |`. `/` sozinho, vazio ou só barras é recusado. O caminho normalizado (sem barra final) é o que aparece nos achados.
- `root_folder_id`: `^[A-Za-z0-9!._-]{1,256}$` e diferente de `.` e `..`.
- `allow_private_networks` é ignorado por este conector para todos os hosts (login, Graph e download).
- Não existe chave de URL base, de host de login, de host do Graph nem de host de download. Os hosts são constantes do módulo.

### 2. Loader e gate de credencial (`config/loader.py`)

- Novo ramo no laço "credential-from-env": se `auth.client_id_from_env` estiver preenchido, chama `_gate_non_rest_env_credential(t, nome, "auth.client_id_from_env")` e `_warn_if_env_from_key_unset_or_empty`, e grava o valor em `auth["client_id"]`, como já é feito com `auth.client_secret_from_env`. Sem regra de prefixo (não é REST, #2164); nome reservado do processo é recusado.
- `_credential_destination_groups`: `sharepoint_online` devolve `None` (destino fixo de fornecedor).
- `_vendor_fixed_destination_groups`: `sharepoint_online` devolve `[{"login.microsoftonline.com"}, {"graph.microsoft.com"}]`, dois destinos distintos. Com `DATA_BOAR_CREDENTIAL_STRICT=1`, os dois precisam estar em `DATA_BOAR_CREDENTIAL_ALLOWED_HOSTS`, e um `allowed_hosts` no YAML, se existir, precisa conter os dois.
- O host de download **não** entra no gate: nenhum token vai para ele. Ele passa só pela allowlist de sufixo e pelo `url_guard` (seção 7).
- Nenhum nome `DATA_BOAR_*` novo é lido direto pelo código.

### 4. Autenticação delegada (device code)

Hosts e escopo (constantes):

- Login: `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/devicecode` e `.../token`.
- Escopo pedido: `https://graph.microsoft.com/Files.Read offline_access` (exatamente essa string, separada por espaço).
- Corpo dos POSTs em `application/x-www-form-urlencoded`, só com `client_id`, `scope` (no devicecode e no refresh), `grant_type`, `device_code` ou `refresh_token`. Nunca `client_secret`.

Quando o device code pode começar: só se as **duas** condições valerem, senão falha `auth_required` sem nenhuma requisição ao login:

1. o processo habilitou o modo interativo (`enable_interactive_sign_in()`, chamado só pela varredura única da CLI; o dashboard web, a API e qualquer agendador nunca chamam); e
2. o fluxo de aviso (padrão `sys.stderr`) é um terminal (`isatty()`).

Mensagem de `auth_required`: "delegated sign-in needs an interactive CLI session (run the scan from a terminal); unattended scans use app-only mode (#2262)".

Aviso ao humano: escrito **direto no fluxo de aviso**, nunca por `logging`, com texto do próprio conector: "To sign in to Microsoft for target '<name>', open <verification_uri> and enter the code <user_code>. The code expires in <N> minutes." Os dois valores vindos do servidor passam por filtro de caracteres imprimíveis. O `message` da Microsoft não é impresso.

Máquina de estados do polling (relógio e `sleep` injetáveis):

| Resposta do `/token` | Ação |
| --- | --- |
| `200` com `access_token` | concluído; guarda os tokens em memória |
| `400` `authorization_pending` | espera `interval` e repete |
| `400` `slow_down` | soma 5 s ao intervalo, espera e repete [H] |
| `400` `authorization_declined` | para; `auth_failed` "Microsoft sign-in was declined" |
| `400` `expired_token` | para; `auth_failed` "Microsoft sign-in code expired" |
| `400` `bad_verification_code` | para; `auth_failed` "device code was not recognised" |
| outro erro com corpo OAuth | para; `auth_failed` "token endpoint error <error> (AADSTS<n>)", só o código e os números de `error_codes`, nunca `error_description` |
| `429`/`5xx` | segue a política da seção 6 dentro do prazo |
| erro de rede | `unreachable` "network error contacting Microsoft login (<NomeDaClasse>)" |
| prazo local estourado | para; `auth_failed` "Microsoft sign-in code expired" |

- `interval`: o da resposta, limitado a 1..60 s; ausente vale 5. Prazo local: `expires_in` limitado a 60..1800 s, contado do envio do devicecode. Nunca há um poll depois do prazo.
- Um `threading.Lock` de módulo serializa o device code: com alvos em paralelo, só um aviso por vez aparece no terminal; o outro worker espera o lock.
- `KeyboardInterrupt` não é capturado.

Token e refresh:

- Os tokens ficam num objeto do conector cujo `__repr__`/`__str__` não mostram valores. Vida: a execução de `run()`; no fim (sucesso ou falha) as referências são apagadas.
- Renovação proativa quando faltam menos de 300 s para `expires_in`. Cada refresh troca o refresh token pelo novo e descarta o antigo.
- `401` do Graph: um refresh e uma única nova tentativa da mesma requisição; um segundo `401` encerra o alvo com `auth_failed` "Microsoft Graph rejected the access token".
- Refresh com `invalid_grant` ou `interaction_required`: se o modo interativo valer, novo device code; senão `auth_failed`.
- Resposta sem `refresh_token` (consentimento sem `offline_access`): segue até o vencimento e então trata como `invalid_grant`.

### 5. Escopo: pasta raiz e travessia

Contenção por construção: o conector resolve a pasta raiz **uma vez** para o par `(driveId, itemId)` e, daí em diante, só anda por id.

1. `GET /v1.0/me/drive` → guarda `drive.id`.
2. Resolução:
   - por caminho: `GET /v1.0/me/drive/root:/{segmentos percent-encoded, um a um, quote(seg, safe="")}`;
   - por id: `GET /v1.0/me/drive/items/{id}`.
3. A raiz resolvida precisa ter a faceta `folder`, não ter `root`, `remoteItem` nem `package`, e ter `parentReference.driveId == drive.id`. Senão `config_error` ("root_folder must be a folder inside the signed-in user's drive"). `404` → `not_found`; `403` → `permission_denied`; os dois encerram o alvo.
4. Travessia em largura: `GET /v1.0/me/drive/items/{id}/children?$top=200`, só a partir da raiz e das subpastas encontradas. O caminho exibido é montado a partir de `root_folder` e dos nomes vistos na travessia; ele serve para exibir, nunca para decidir.
5. Cada filho:
   - `remoteItem`, `package`, `malware` ou `deleted` presentes → ignorado (não lista dentro, não baixa); conta no resumo.
   - `parentReference.driveId` diferente de `drive.id` → ignorado; conta no resumo.
   - `folder` → entra na fila se a profundidade for menor que `max_depth` e o id ainda não foi visto.
   - `file` → filtro de extensão (mesmo do conector de arquivos) e de tamanho; depois download.
   - sem `file` nem `folder` → ignorado.
6. Nenhuma requisição usa endereço por caminho depois da resolução, nem `/me/drive/root/children`, nem pesquisa (`search`), nem `delta`.
7. No fim, uma linha INFO no log de auditoria só com contagens: listados, baixados, ignorados por motivo. Sem nomes de arquivo.

Método público usado pelo `run()` e pelo roteiro da Fase 0:

```python
def list_scope(self) -> list[ScopeEntry]: ...
# ScopeEntry: display_path: str, size: int, kind: Literal["file", "folder"], skipped_reason: str | None
```

`list_scope()` autentica, resolve e percorre sem baixar nada.

### 6. Chamadas ao Graph

Todas para `https://graph.microsoft.com/v1.0/...`, com `Authorization: Bearer <access>` por requisição (nunca como cabeçalho padrão do cliente) e `User-Agent` de `core.about.get_http_user_agent()`. Timeout de 30 s.

| Resposta | Ação |
| --- | --- |
| `200` | segue |
| `302` (só em `/content`) | seção 7 |
| `401` | um refresh e uma nova tentativa (seção 4) |
| `403` | na raiz: encerra `permission_denied`. Numa subpasta ou arquivo: `save_failure` daquele caminho e segue |
| `404` | na raiz: encerra `not_found`. Num item: falha daquele caminho e segue |
| `429` ou `503` | espera `Retry-After` (inteiro em segundos, limitado a `throttle_max_wait_seconds`); sem cabeçalho ou inválido, backoff 1, 2, 4, 8, 16 s (com o mesmo teto); no máximo 5 tentativas; esgotou → `throttled` naquele item, ou no alvo se for a raiz |
| outro `5xx` | backoff 1, 2, 4 s; 3 tentativas; esgotou → `unreachable` |
| erro de rede | `unreachable` com o nome da classe, sem URL |

`@odata.nextLink`: antes de seguir, exige `https`, host exatamente `graph.microsoft.com`, porta ausente ou 443, caminho começando com `/v1.0/` e sem userinfo. Fora disso: `scope_violation` "unexpected @odata.nextLink rejected", a requisição não é feita e o `Authorization` não sai. Um `nextLink` repetido na mesma listagem encerra aquela listagem com `scope_violation`. Limite de 10 000 páginas por pasta.

### 7. Download

1. `GET /v1.0/me/drive/items/{id}/content` com `Authorization`, cliente com `follow_redirects=False`.
2. `200`: o corpo é o conteúdo (veio do Graph).
3. `302`: lê `Location`. Exige URL absoluta `https`, sem userinfo, porta ausente ou 443, e host que termine em um sufixo da allowlist de download: `.files.1drv.com` e `.sharepoint.com` [H]. Fora disso: `scope_violation` "download host not allowlisted: <host>" (só o host, nunca o caminho nem a query) e a requisição não é feita.
4. O host aprovado passa por `resolve_and_validate_outbound_url(..., allow_private=False)`, sempre, ignorando `allow_private_networks`. Recusado → `scope_violation`.
5. O GET da `Location` usa **outro** cliente, sem `Authorization` e sem cookies, com o pin de IP do passo 4 e `follow_redirects=False`. Não depende do httpx tirar o cabeçalho num redirect.
6. Leitura em fluxo, com teto de `max_file_bytes`. Item com `size` acima do teto é ignorado antes do download (`skipped` "file larger than max_file_bytes"); conteúdo que passa do teto no fluxo é abortado e o temporário apagado.
7. `401`, `403`, `404` ou `410` na `Location` (URL vencida): um novo `/content` e uma nova tentativa; de novo falhou → `save_failure` daquele caminho.
8. O temporário fica num diretório criado com `tempfile.mkdtemp()` (modo 0700), é apagado no `finally` de cada arquivo, e o diretório é apagado no fim de `run()`.
9. Logs do httpx: o conector instala, uma vez, um `logging.Filter` no logger `httpx` que troca, em qualquer registro, a URL de um host da allowlist de download por `https://<host>/<redacted>`. Não altera registros de outros hosts.

### 8. Tokens, códigos e segredos

- Só memória (DEC-1). Nenhuma chave de config para gravar token em disco; nada em `~/.cache`, no diretório de saída, no SQLite ou no relatório.
- Nunca aparecem em log (qualquer logger, qualquer nível), em `save_failure`, em `save_finding`, em `stdout`/`stderr`, em exceção que saia de `run()` nem no `repr` do conector: access token, refresh token, `device_code`, `client_id` e a URL de download (caminho e query).
- Única exceção: `user_code` e `verification_uri` vão para o fluxo de aviso do humano, e só para ele.
- `run()` não deixa escapar exceção do httpx nem de JSON malformado: tudo vira `save_failure` com mensagem fixa desta seção e das seções 4, 6 e 7. Nenhuma mensagem é montada com `str(e)`, `repr(e)`, URL completa ou corpo de resposta (gate #1722 e `tests/str_e_callsite_gate.py`).
- Defesa em profundidade fora do conector (endurecer `redact_secrets_for_log` para `Bearer` e URLs pré-autenticadas) é pedida ao PM como tarefa à parte; este desenho não depende dela.

### 10. Saídas

Achados: `save_finding("filesystem", target_name=<name>, path=<display_path>, file_name=<nome>, data_type=<EXT>, sensitivity_level, pattern_detected, norm_tag, ml_confidence)`, o mesmo formato do SharePoint on-prem. `display_path` = `onedrive:` + `root_folder` + caminho relativo (ex.: `onedrive:/DataBoar-Sintetico/sub/a.txt`). Sem id de item, id de drive, e-mail, nome de conta ou URL.

Falhas: `save_failure(target_name, reason, detail)` com `reason` deste conjunto fechado:

| `reason` | Quando | Encerra o alvo? |
| --- | --- | --- |
| `config_error` | validação da seção 1, raiz inválida | sim |
| `auth_required` | sem sessão interativa | sim |
| `auth_failed` | negado, expirado, erro OAuth, 401 repetido | sim |
| `permission_denied` | 403 | na raiz sim; num item não |
| `not_found` | 404 | na raiz sim; num item não |
| `throttled` | 429/503 esgotado | na raiz sim; num item não |
| `unreachable` | rede ou 5xx esgotado | no login e na raiz sim; num item não |
| `scope_violation` | nextLink, host de download ou raiz fora das regras | nextLink: só aquela listagem; download: só aquele arquivo |
| `skipped` | arquivo maior que o teto | não |

## Riscos e pontos de atenção

- O engine grava `clean_error(e)` de qualquer exceção que escape de `run()`, e `clean_error` não remove `tempauth` nem `Bearer` [T]. Por isso nenhuma exceção pode escapar com URL ou token dentro.
- O logger `httpx` registra a URL inteira em INFO [T]; sem o filtro da seção 7, um handler no logger raiz (por exemplo, num deploy com log em DEBUG) gravaria a URL de download.
- Comparar caminhos por prefixo de texto deixa `/Pasta2` passar por `/Pasta`; a travessia por id evita isso, e o D-31 cobre.
- `@odata.nextLink` e `Location` vêm do servidor: são o mesmo vetor de um override de URL base. Os dois têm regra de host própria.
- Com alvos em paralelo, o polling ocupa um worker por até 30 minutos (teto do prazo); o lock evita avisos misturados, não a espera.
- Refresh token: 90 dias, não preso a recurso, o antigo não é revogado [V]. Em disco, seria uma credencial do drive inteiro; por isso só memória.
- O dashboard web iniciado de um terminal tem `stderr` em TTY; por isso a condição 1 da seção 4 (opt-in só da CLI) é necessária, e o D-51 cobre.
- `main.py` e `config/loader.py` são arquivos grandes e muito usados: mudança mínima, só o descrito na seção 3.

## Decisões

Registradas aqui; o ADR correspondente (próximo número livre em `docs/adr/`, com o inventário assinado regerado) é pedido ao PM, porque `docs/adr/INVENTORY.txt` é assinado e o índice é testado.

- **DEC-1** Tokens só em memória, pela vida de `run()`. Motivo: o refresh token vale 90 dias, serve para qualquer recurso consentido e o antigo não é revogado; `Files.Read` lê o drive inteiro.
- **DEC-2** Escopo imposto pelo conector: `root_folder` obrigatório e nunca a raiz; resolução única para `(driveId, itemId)`; travessia só por id; `remoteItem`, `package` e outro `driveId` ignorados.
- **DEC-3** `Files.Read`, não `Files.Read.AppFolder`. Motivo: a variante de pasta do app conhecida é `Files.ReadWrite.AppFolder` (dá escrita e é só de conta pessoal); a de leitura não foi confirmada [H]; e confinar à pasta do app não prova o caso de uso, em que o dado do cliente nunca está nessa pasta. A restrição real fica no conector (DEC-2) e, na #2262, em `Sites.Selected`.
- **DEC-4** Download por cliente separado, sem `Authorization`, com allowlist de sufixo de host, `url_guard` sem opt-in de rede privada e filtro no logger `httpx`.
- **DEC-5** Device code só com opt-in da CLI e terminal; sem isso, falha imediata. Varredura sem humano é app-only (#2262).
- **DEC-6** Hosts fixos, sem chave de URL base; o simulado entra por `httpx.MockTransport` numa costura só de palavra-chave que o engine não passa.
- **DEC-7** Gate de credencial com destino fixo de fornecedor: login e Graph, dois grupos.
- **DEC-8** Porta aberta para a #2262: `auth.mode` (`delegated`; `app_only` recusado por enquanto) e `drive` (`me`; outros recusados por enquanto), sem mudar o tipo.
